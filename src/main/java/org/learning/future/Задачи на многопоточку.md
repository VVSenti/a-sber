## Задача 1
Есть список из 100 заказов. Для каждого заказа нужно выполнить условно «долгую» операцию — например, получить информацию о клиенте из БД и рассчитать стоимость заказа.

Необходимо:

создать ExecutorService с фиксированным количеством потоков;
отправить задачи на выполнение через submit();
получить результаты через Future;
собрать результаты в общий список;
корректно завершить ExecutorService;
обработать InterruptedException и ExecutionException.

Что обсудить с кандидатом:

почему здесь лучше submit(), а не execute();
что произойдет, если вызвать future.get() сразу после каждого submit();
как подобрать размер пула;
что произойдет при shutdown() / shutdownNow();
как не потерять interrupt-флаг.

Усложнение: добавить timeout при получении результата через future.get(timeout, unit).

## Задача 2

Есть 10 потоков. Каждый поток 10 000 раз увеличивает общий счетчик.

Дан код:
class Counter {
	private int value = 0;

	public void increment() {
		value++;
	}

	public int getValue() {
		return value;
	}
}

Нужно запустить инкременты параллельно через ExecutorService и добиться гарантированного результата 100_000.

Кандидат должен предложить несколько вариантов решения:

synchronized;
AtomicInteger;
LongAdder.

Что проверить:

понимает ли кандидат, почему value++ не является атомарной операцией;
разницу между volatile и AtomicInteger;
когда LongAdder предпочтительнее AtomicInteger;
что происходит с производительностью при большом количестве конкурентных обновлений.

Хорошее дополнительное задание: попросить кандидата объяснить, почему простое добавление volatile проблему не решает.

## Задача 3

Есть список строк, содержащих сообщения:

"ERROR database connection"
"INFO user logged in"
"ERROR timeout"
"INFO user logged out"
...

Нужно параллельно обработать сообщения и посчитать количество сообщений каждого типа (INFO, ERROR, WARN).

Использовать ExecutorService и ConcurrentHashMap.

Например, ожидаемый результат:
INFO -> 5000
ERROR -> 3000
WARN -> 2000

Важно: нельзя использовать обычный HashMap с несколькими потоками.

Попросить кандидата реализовать, например:
map.merge(type, 1, Integer::sum);

Что проверить:

зачем здесь ConcurrentHashMap;
чем ConcurrentHashMap отличается от Collections.synchronizedMap();
насколько потокобезопасна конструкция get() + put();
почему merge() подходит для данной задачи;
можно ли использовать AtomicInteger в качестве значения map.

Усложнение: сделать так, чтобы каждый worker обрабатывал свою часть списка, а затем результаты агрегировались.

## Задача 4

Запуск задачи только после завершения нескольких потоков — CountDownLatch

Условие: Есть сервис, который перед началом работы должен дождаться загрузки трех независимых компонентов:

конфигурации;
справочников;
кэша.

Каждый компонент загружается в отдельном потоке и занимает случайное количество времени. Главный поток не должен начинать работу, пока все три компонента не загрузятся.

Использовать:
ExecutorService
CountDownLatch

Схема примерно такая:
         ┌─ Config ─────┐
         │     │
Start ───┼─ Dictionaries├──→ Application starts
         │    │
         └─ Cache ──────┘

Что проверить:

понимание CountDownLatch;
зачем нужен countDown();
где использовать await();
что произойдет, если одна из задач завершится с исключением;
можно ли переиспользовать CountDownLatch;
чем CountDownLatch отличается от CyclicBarrier.

Усложнение: добавить timeout на ожидание загрузки компонентов и корректную обработку ситуации, когда один из компонентов не загрузился.

public class ReportService {

	private final ExecutorService executor = Executors.newFixedThreadPool(10);
